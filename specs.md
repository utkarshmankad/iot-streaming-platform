# Environmental IoT streaming platform

**Version 0.1 · Implementation specification**

## 1. Scope and workload

- **REQ-01.** Run the simulator, edge gateway, Java backend, TimescaleDB and React frontend as separate services in one Docker Compose project on a laptop. Serve the React build from a container at `http://127.0.0.1:8080` and reverse-proxy its API requests to Java. Keep database and service ports on internal networks. Bind an optional authenticated sensor ingress to a configured LAN address only when testing external hardware. No cloud runtime dependencies after initial builds and image pulls.
- **REQ-02.** Each enabled sensor stream emits one reading per second. The simulator supports temperature (°C), relative humidity (%), pressure (hPa) and particulate matter PM2.5 (µg/m³). Use deterministic seeds, configurable counts, realistic variation and staggered emission phases. A stream has one stable sensor ID and measurement type. A multi-channel physical device can expose multiple streams.
- **REQ-03.** Target 1.0 decimal GB per 24 hours of active runtime (±5%), measured as UTF-8 bytes of distinct accepted sensor telemetry bodies before transport framing, batching and compression. Record retries and network bytes independently. At 256 bytes per reading, 45 streams yield 45 readings/s, 3.888 million readings and 995.3 MB/day, or 58.32 million readings and 14.93 GB across 15 days. Calibrate stream count from measured mean record size and record the actual distribution. Track database, indexes, WAL, volumes and logs separately from payload bytes.
- **REQ-04.** Provide a low-volume demo profile and a real-time soak profile. Keep the soak fleet enabled during the baseline. Use a separate control-test sensor or record control intervals explicitly. Real hardware support starts with one documented adapter when a model and protocol are available. The synthetic run is the reproducible scale benchmark.

## 2. Data path and delivery

- **ING-01.** Use HTTP JSON from simulator or device adapter to the gateway and bounded HTTP JSON batches from gateway to Java. Use Java with Spring Boot, Gradle, Flyway and JDBC batched inserts for the backend. Contract schemas are versioned and shared via checked-in JSON Schema and OpenAPI. A reading contains `schemaVersion`, `sensorId`, immutable `eventId`, `observedAt` (UTC, millisecond precision), and finite numeric `value`. Registry supplies type, unit and owning gateway. Reject unknown IDs, malformed values and clock skew greater than two minutes into the future. Preserve event time across retries. Record gateway receive time and backend receive time separately.
- **ING-02.** Gateway acknowledges after a durable enqueue in a SQLite spool on a named volume. Sender retries with the same IDs on timeouts or backpressure. Gateway flushes at 250 events or one second, whichever comes first. Java validates each entry and responds with committed, duplicate or permanent rejection per event only after the valid rows commit. Transfer is at least once. Remove entries from the spool only after confirmed outcomes. Retry ambiguous failures with bounded exponential backoff and jitter. Record permanent rejections with reason without logging payloads. On a full spool return retryable backpressure, surface an alert and count producer drops explicitly if its bounded buffer also fills.
- **ING-03.** Timescale hypertable `readings` partitions on `observed_at TIMESTAMPTZ`. Start with one-day chunks and index access by sensor and time. Use a unique key `(sensor_id, observed_at, event_id)` and idempotent inserts; an event's observed timestamp and value are immutable on retry. Keep sensor registry, command audit and outbox in regular relational tables. Persist database, spool and simulator sequence/checkpoints; orderly restarts preserve accepted, unacknowledged readings. Verify constraints with the chosen pinned Timescale image. [Hypertable index rules](https://github.com/timescale/docs/blob/latest/use-timescale/hypertables/hypertables-and-unique-indexes.md)
- **ING-04.** Require per-gateway credentials and bind ingress IDs to their registered source. Use a generated local operator login with a session cookie and CSRF protection. Require TLS for LAN hardware ingress. Keep credentials outside Git, and publish sample configuration with placeholders.

## 3. Trends and sensor controls

- **UI-01.** React and TypeScript dashboard lists registered sensors with type, unit, last seen, connectivity, desired state and confirmed state. Users filter by sensor, metric and time range. Plot min, max and mean with sample count in tooltips, show gaps and distinguish partial buckets. Show loading, no-data, stale and error states. Refresh visible trends approximately every 15 seconds.
- **UI-02.** `GET /api/v1/trends?sensorId=…&from=…&to=…&bucket=15m|1h|1d|1w` returns bucket boundaries, count, min, max, mean and freshness. Use half-open time ranges and UTC-aligned buckets with weeks beginning Monday. Require bucket-aligned bounds, with the UI rounding the selected bounds and showing the effective range. Limit history to 30 days and requests to 10 sensors. Mark the in-progress bucket and return null statistics with count zero for gaps. Display timestamps with an explicit timezone.
- **UI-03.** Materialize 15-minute per-sensor count, sum, min and max. Derive hourly, daily and weekly trends with weighted means (`sum(sum) / sum(count)`). Combine materialized buckets and raw data for the recent tail without double counting. Refresh the last 48 hours every minute. Schedule an explicit affected-bucket refresh for older accepted replays within retained history. Expose freshness after delayed data arrives. Keep raw telemetry for at least 30 days and disable expiry during the soak. [Continuous aggregate refresh policies](https://github.com/timescale/docs/blob/latest/use-timescale/continuous-aggregates/refresh-policies.md)
- **CTL-01.** `GET /api/v1/sensors` returns registry and status. `POST /api/v1/sensors/{id}/commands` accepts an idempotency key and `enabled: true|false`, atomically stores the desired state and a durable command, and returns HTTP 202 and a command ID. `GET /api/v1/commands/{id}` exposes pending, applied, failed, expired and superseded status. Gateway polls for commands and forwards them to the registered adapter. Device ACK includes command ID, version and actual state. Persist the last applied version at the adapter. Duplicate deliveries are idempotent, and stale versions and acknowledgments cannot overwrite newer state. Commands expire after 60 seconds by default. Authorize operator actions and audit actor, timestamps, outcome and errors.
- **CTL-02.** On/off means enable or pause sampling while the control channel and heartbeat stay alive. A hardware adapter can offer power switching when a separate reachable controller can restore power. Expose capability per sensor, with control buttons disabled for unsupported hardware. After a confirmed pause, previously buffered readings may still arrive with earlier event times. History remains readable. Show pending, failure, offline and timeout explicitly. Reconcile observed state on reconnect. Flag a device offline after three missed five-second heartbeats.

## 4. Laptop scale experiment

- **OPS-01.** Document one-command startup and health checks, configuration, shutdown preserving volumes, and explicit reset. Pin images and dependencies and verify native architecture availability for the laptop. Initial planning budget is 4 Docker vCPUs, 8 GiB RAM and at least 50 GB free in both host and Docker storage accounting. Adjust from pilot measurements. Bound container logs and gateway spool (initial cap 1 GB). Alert when projected disk usage leaves less than 10 GB at the end of the run. Keep the laptop plugged in and awake; record host sleep and service downtime.
- **OPS-02.** Run a 1-hour calibration, then a 24-hour pilot before the 15-day soak. Capture laptop model, architecture, Docker limits, image versions, config, seed, start/end timestamps and interruptions. Record per-minute throughput, committed events and bytes, duplicate/rejected/dropped events, gateway backlog bytes and age, latency percentiles, CPU, memory, database and index size, WAL, volume space and log growth. Record warm and cold trend-query timings each day at the same concurrency and query shapes.
- **OPS-03.** Use 15 active workload days (~15 GB / ~58 million readings under the example payload). Preserve a timeline of wall-clock outages. Report any extensions used to reach 15 active days separately from uninterrupted runtime. Exercise a two-minute backend outage and a gateway restart under sustained workload in the pilot or a separately marked fault interval. Reconcile producer, spool and committed counts after drain. Compare day 1, 7 and 15 and export a local CSV and Markdown summary of growth, latency and errors. Keep results and volumes out of Git.

## 5. Acceptance and implementation order

| ID | Acceptance for the initial laptop run |
|---|---|
| AC-01 | Compose starts from a clean clone. Browser displays seeded telemetry across all four resolutions. Restart restores data and sensor state. |
| AC-02 | Soak stays within ±5% of 1 GB/day over active runtime. Reconcile all generated and committed events after drain, with zero unexplained losses and zero duplicate rows. Backlog drains within 5 minutes after the two-minute fault test. |
| AC-03 | During steady state, p95 gateway receipt to commit ≤3 s and p95 trend API latency ≤500 ms with five concurrent readers across representative time ranges and all resolutions. Document the exact test mix and measure again at day 15. |
| AC-04 | Validate bucket edges, weekly boundaries, weighted means, late arrivals and gaps against deterministic fixtures. Fresh committed data becomes visible in the current trend within 30 s under steady load. |
| AC-05 | Online sensor commands reach confirmed state within 5 s at p95. Pause stops new samples, resume restarts them and an offline command cannot report success without ACK. Test duplicate requests, stale versions, restart and expired commands. |
| AC-06 | The run report explains resource growth, interruptions, retention and capacity bottlenecks with measured data. CI checks the short test workloads. The 15-day run executes locally. |

Implementation sequence: M0 repository, rules and Compose skeleton; M1 simulator, durable gateway and Java/Timescale ingest; M2 aggregated API and React trends; M3 acknowledged sensor controls and fault tests; M4 calibration, pilot, soak and report. Split milestones into single-task PRs and track them in `plan.md`. Suggested source paths: `simulator/`, `gateway/`, `backend/`, `frontend/`, `perf/` and `scripts/`.

## 6. GitHub branching and CI

Reference: [Invoice Intel CI policy at the reviewed commit](https://github.com/utkarshmankad/invoice-intel/blob/c62b77ab8dccabffa43323ac5ef5dc7573e9a50f/docs/ci.md).

- **GIT-01.** Use protected, releasable `main` and short-lived branches named `<type>/<task-id>-<description>` with one task per PR. Rebase behind branches and tag releases on `main`. Use configuration flags for incomplete multi-PR features. Require Conventional Commit PR titles and list requirement IDs in the body.
- **GIT-02.** Apply the Invoice Intel `main-trunk` ruleset to the default branch after the first bootstrap commit and a verified CI run. Require PRs, squash-only merges, linear history, resolved review threads, zero required approvals and the strict GitHub Actions check `CI gate`. Block force-push and deletion of `main`. Use zero bypass actors and auto-delete merged branches. Enable Dependabot, secret scanning and push protection where available. Verify ruleset and security-feature availability for the chosen GitHub visibility and plan before marking M0 complete.
- **CI-01.** Trigger CI on PRs to `main`, pushes to `main` and manual dispatch. Cancel superseded PR runs. Use least-privilege permissions and SHA-pinned actions. Run PR hygiene, tracked secrets/data guards and gitleaks, actionlint, Spotless, Java unit/ArchUnit and Testcontainers integration tests, merged JaCoCo line coverage ≥85%, SpotBugs/FindSecBugs, CodeQL, high/critical dependency and GPL/AGPL review, hadolint, Trivy fixable high/critical image scan, Compose smoke test and Gatling performance assertions. Add frontend type-check, ESLint, unit tests and production build. Adapt the Invoice Intel data guard to forbid captured telemetry, secrets, database files and benchmark outputs.
- **CI-02.** `CI gate` summarizes all jobs, runs even if dependencies fail, and rejects failed or cancelled jobs. Permit intentional prerequisite skips before build components exist. Once a component lands, its expected checks must fail if build inputs disappear. Docs-only PRs skip performance only. Run the Compose smoke test with synthetic sensors and disposable credentials. Verify startup, authorized ingest and trend read, duplicate replay, and a sensor off/on round trip as those capabilities land. Publish CI reports for 14 days.
- **CI-03.** Nightly at 03:00 IST, run PIT on critical ingestion and control code and rescan fresh images with Trivy. Nightly jobs are outside the merge gate. Add CODEOWNERS, a PR template and weekly grouped Dependabot updates for Gradle, npm, Docker and Actions.
