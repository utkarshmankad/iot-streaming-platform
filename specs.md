# Environmental IoT streaming platform

**Version 0.5 · Implementation specification**

## 1. Scope and workload

- **REQ-01.** Run the simulator, MQTT broker, edge gateway, Java backend, TimescaleDB and React frontend as separate services in one Docker Compose project on a laptop. Serve the React build from a container at `http://127.0.0.1:8080` and reverse-proxy its API requests to Java. Keep database and service ports on internal networks. All telemetry is generated by the simulator. It runs on the Compose network and requires no physical sensors or internet connection after initial builds and image pulls.
- **REQ-02.** Each enabled sensor stream emits one reading per second. The simulator supports temperature (°C), relative humidity (%), pressure (hPa) particulate matter PM2.5 (µg/m³), ambient light (lux) and ambient oxygen concentration (% by volume). Use deterministic seeds, configurable counts, realistic variation and staggered emission phases. A stream has one stable sensor ID and measurement type. Include at least one simulated stream of each type in the demo profile.
- **REQ-03.** Target 1.0 decimal GB per 24 hours of active runtime (±5%), measured as bytes of distinct accepted binary Protobuf telemetry payloads before transport framing, batching and compression. Record retries and network bytes independently. For example, a measured mean of 90 bytes implies about 129 one-hertz streams, 11.15 million readings/day and 167.18 million readings over 15 active days. Recompute row counts after calibration. Calibrate stream count from measured mean record size and record the actual distribution. Track database, indexes, WAL, volumes and logs separately from payload bytes.
- **REQ-04.** Provide a low-volume demo profile and a real-time soak profile. Keep the soak fleet enabled during the baseline. Use a separate control-test sensor or record control intervals explicitly. Distribute the soak workload across at least two simulated tenants and record each tenant's contribution to the shared 1 GB/day target.

## 2. Data path and delivery

- **ING-01.** Use MQTT 5 over TCP through a private broker for the simulator-to-gateway link. Telemetry, heartbeats, receipts and sampling commands use binary Protobuf payloads and tenant-scoped topics. The gateway sends bounded HTTP batches with Protobuf bodies to Java. Browser APIs use HTTP JSON. Use Java with Spring Boot, Gradle, Flyway and JDBC batched inserts for the backend. Check in versioned Protobuf definitions, sensor-type validation rules and browser OpenAPI contracts. A reading contains `schemaVersion`, `sensorId`, immutable `eventId`, `observedAt` (UTC, millisecond precision), and finite numeric `value`. Validate **every individual event** at both gateway ingress and backend batch intake using the versioned Protobuf contract and sensor-specific validation rules. Check parseability, payload size, explicit required-field presence, types, UTC epoch milliseconds and type-specific value bounds, including 0–100% for humidity and oxygen and nonnegative lux for light. Resolve tenant, type, unit and gateway ownership from authenticated identity and the tenant-scoped registry. Reject unknown IDs or unsupported versions and enforce the configured future clock-skew limit of two minutes. In a mixed batch, reject only invalid entries and return machine-readable reasons. Preserve event time across retries. Record gateway receive time and backend receive time separately.
- **ING-02.** Publish telemetry at MQTT QoS 1. The simulator retains the original bytes and event ID until it receives a correlated application receipt. Gateway sends accepted only after a durable enqueue in its SQLite spool on a named volume. MQTT PUBACK confirms transport delivery to the receiving peer. It does not confirm the gateway spool commit. Sender retries with the same IDs on timeouts or backpressure. Gateway flushes at 250 events or one second, whichever comes first. Java validates each entry and responds with committed, duplicate or permanent rejection per event only after the valid rows commit. Transfer is at least once. Remove entries from the spool only after confirmed outcomes. Retry ambiguous failures with bounded exponential backoff and jitter. Record permanent rejections with reason without logging payloads. On a full spool return retryable backpressure, surface an alert and count producer drops explicitly if its bounded buffer also fills.
- **ING-03.** Timescale hypertable `readings` partitions on `observed_at TIMESTAMPTZ`. Start with one-day chunks and index access by tenant, sensor and time. Use a hypertable unique key `(tenant_id, sensor_id, observed_at, event_id)` and a relational receipt ledger keyed by `(tenant_id, sensor_id, event_id)` with a canonical event fingerprint. Insert the receipt and reading in the same transaction using the ledger uniqueness constraint to serialize concurrent replays. Identical replays return duplicate success, including after a lost response. Reusing an event ID with changed content returns a permanent conflict, even if the timestamp changed. Retain receipt identities for at least the full raw-data retention and supported replay window. The simulator persists generated events until durable gateway acceptance and reuses their complete original contents on retry. Keep sensor registry, command audit and outbox in regular relational tables. Persist database, spool and simulator sequence/checkpoints; orderly restarts preserve accepted, unacknowledged readings. Verify constraints with the chosen pinned Timescale image. [Hypertable index rules](https://github.com/timescale/docs/blob/latest/use-timescale/hypertables/hypertables-and-unique-indexes.md)
- **ING-04.** Require per-device MQTT credentials and topic ACLs, separate gateway credentials, and registry checks that bind topic IDs to the registered source. Store MQTT authorization as a projection of the database registry. Use a generated local operator login with a session cookie and CSRF protection. Keep credentials outside Git, and publish sample configuration with placeholders.

## 3. Trends and sensor controls

- **UI-01.** React and TypeScript dashboard provides a tenant selector for operators with multiple memberships and lists that tenant’s registered sensors with type, unit, last seen, connectivity, desired state and confirmed state. Users filter by sensor, metric and time range. Plot min, max and mean with sample count in tooltips, show gaps and distinguish partial buckets. Show loading, no-data, stale and error states. Refresh visible trends approximately every 15 seconds.
- **UI-02.** `GET /api/v1/trends?sensorId=…&from=…&to=…&bucket=15m|1h|1d|1w` returns bucket boundaries, count, min, max, mean and freshness. Use half-open time ranges and UTC-aligned buckets with weeks beginning Monday. Require bucket-aligned bounds, with the UI rounding the selected bounds and showing the effective range. Limit history to 30 days and requests to 10 sensors. Mark the in-progress bucket and return null statistics with count zero for gaps. Display timestamps with an explicit timezone.
- **UI-03.** Materialize 15-minute per-tenant, per-sensor count, sum, min and max. Derive hourly, daily and weekly trends with weighted means (`sum(sum) / sum(count)`). Combine materialized buckets and raw data for the recent tail without double counting. Refresh the last 48 hours every minute. Schedule an explicit affected-bucket refresh for older accepted replays within retained history. Expose freshness after delayed data arrives. Keep raw telemetry for at least 30 days and disable expiry during the soak. [Continuous aggregate refresh policies](https://github.com/timescale/docs/blob/latest/use-timescale/continuous-aggregates/refresh-policies.md)
- **CTL-01.** `GET /api/v1/sensors` returns registry and status. `POST /api/v1/sensors/{id}/commands` accepts an idempotency key and `enabled: true|false`, atomically stores the desired state and a durable command, and returns HTTP 202 and a command ID. `GET /api/v1/commands/{id}` exposes pending, applied, failed, expired and superseded status. Gateway polls the backend for commands and forwards them to the registered simulator stream over MQTT. Device ACK includes command ID, version and actual state. Persist the last applied version in the simulator. Duplicate deliveries are idempotent, and stale versions and acknowledgments cannot overwrite newer state. Commands expire after 60 seconds by default. Authorize operator actions and audit actor, timestamps, outcome and errors.
- **CTL-02.** On/off means enable or pause sampling while the control channel and heartbeat stay alive. Every simulated sensor supports these sampling controls. After a confirmed pause, previously buffered readings may still arrive with earlier event times. History remains readable. Show pending, failure, offline and timeout explicitly. Reconcile observed state on reconnect. Flag a device offline after three missed five-second heartbeats.

## 4. Laptop scale experiment

- **OPS-01.** Document one-command startup and health checks, configuration, shutdown preserving volumes, and explicit reset. Pin images and dependencies and verify native architecture availability for the laptop. Initial planning budget is 4 Docker vCPUs, 8 GiB RAM and a 50 GB free-space floor for host and Docker storage. Raise that floor before the soak if pilot projections for the database, WAL, and both queues require more space. Budget the independent backup target separately. Adjust from pilot measurements. Bound container logs and gateway spool and simulator outbox (size both using OPS-04). Alert when projected disk usage leaves less than 10 GB at the end of the run. Keep the laptop plugged in and awake; record host sleep and service downtime.
- **OPS-02.** Run a 1-hour calibration, then a 24-hour pilot before the 15-day soak. Capture laptop model, architecture, Docker limits, image versions, config, seed, start/end timestamps and interruptions. Record per-minute throughput, committed events and bytes, duplicate/rejected/dropped events, gateway backlog bytes and age, latency percentiles, CPU, memory, database and index size, WAL, volume space and log growth. Record warm and cold trend-query timings each day at the same concurrency and query shapes.
- **OPS-03.** Use 15 active workload days (~15 GB of binary telemetry; reading count comes from calibration). Preserve a timeline of wall-clock outages. Report any extensions used to reach 15 active days separately from uninterrupted runtime. Exercise a two-minute backend outage and a gateway restart under sustained workload in the pilot or a separately marked fault interval. Reconcile producer, spool and committed counts after drain. Compare day 1, 7 and 15 and export a local CSV and Markdown summary of growth, latency and errors. Keep results and volumes out of Git.

### Multi-day outages and recovery

- **OPS-04.** Design for seven days of continuous generation during loss of gateway-to-backend connectivity, followed by replay. WAN loss alone must have no impact on the local Compose path. Provision the gateway spool for at least 10 decimal GB usable, or 1.3 times the measured seven-day on-disk spool growth, whichever is greater. Size the simulator outbox by the same rule for a gateway outage. Include SQLite overhead, live database growth and backup space in preflight checks. A full queue applies backpressure and never evicts acknowledged data. Log and count any samples the simulator must drop after exhausting its own durable capacity. Throttle replay per tenant while accepting live traffic. Target a total commit rate of at least 4× steady load during recovery, enough to drain a seven-day backlog within three days. Refresh affected historical buckets and reconcile per-tenant generated, rejected, duplicate, dropped, queued and committed counts.
- **OPS-05.** Take a daily PostgreSQL/TimescaleDB-aware backup and archive WAL to an independent, encrypted storage target, such as a mounted external drive usable offline. Use a database-consistent base backup and continuous WAL archiving for point-in-time recovery. Snapshot the SQLite spool and simulator outbox using their database backup mechanism. Include registry, command and receipt state, migrations, pinned versions and recoverable configuration. Keep backups through the soak and final verification, with at least 30 days of retention. Verify checksums and alert on missing archives, stale backups or low space. Define an RPO of at most 15 minutes for the backend while WAL archival is healthy and 24 hours for catastrophic loss of producer or spool storage with daily snapshots. A service outage with intact volumes must preserve durably accepted events. Report actual recovery gaps when independent storage or archival is unavailable.
- **OPS-06.** Target restore of a queryable stack within four hours of replacement resources becoming available, with backlog drain measured separately. Restore into isolated Compose volumes before promotion. Pause writes and command dispatch, restore the database and queue snapshots, verify schema and tenant isolation, and replay available events with original IDs. Rebuild affected aggregate buckets. Invalidate pre-restore pending commands and reconcile current simulator state and command versions before accepting new control requests. Compare restored counts and timestamps against the backup manifest and spool, record any unfillable gaps, then reopen access. Run a restore drill during the pilot.

| Failure | Expected behavior |
|---|---|
| Enabled sensor stops emitting while heartbeats continue | Mark stream stale after 10 seconds without a new sample and show a chart gap. Track sample freshness and heartbeat independently. A paused sensor shows its confirmed pause state. |
| Simulator crashes or loses gateway access | Show offline when heartbeats expire. Restart from persisted outbox and sequence state. Keep a true gap for samples never generated while the simulator was down. |
| WAN unavailable for days | Ingest, trends and controls continue over Compose networking. A mounted backup target can continue receiving backups offline. |
| Gateway cannot reach backend for days | Spool durably, alert on backlog age and capacity, recover with throttled replay. Show telemetry staleness and pending or expired commands. |
| Backend or database unavailable, or commit ACK lost | Retry unconfirmed batches without losing acknowledged data or duplicating committed readings. Keep health reporting distinct from data freshness. |
| Malformed, conflicting or delayed events | Reject invalid or conflicting events explicitly. Admit valid late events inside the retention window and repair affected trend buckets. |
| Disk pressure, queue saturation or corrupted volume | Alert before capacity exhaustion, preserve durable queued data, and restore damaged state from the independent backup. Record any unrecoverable event range. |
| Duplicate, expired or out-of-order control requests | Apply a valid command once. Reject stale deliveries and reconcile reported state after reconnect or restore. |
| One tenant floods ingress or trends | Enforce per-tenant limits and fair scheduling so other tenants retain queue capacity and access. |

### Observability, alerts and alarms

- **OBS-01.** Monitor generated, accepted and committed counts and bytes, validation failures, duplicates, drops, MQTT reconnects and receipt age, queue depth and oldest event age, database commit latency, trend freshness and query latency, command outcomes and ACK latency, backup and WAL age, and host/container resource consumption. Track reading freshness separately from heartbeats. Retain local metrics for at least 30 days and export daily snapshots for the soak report.
- **OBS-02.** Keep a warning and critical severity policy with threshold, duration, recovery condition and runbook action. Raise warnings for stalled delivery, reduced ingest, stale aggregates or capacity pressure. Raise critical alarms for data loss, sustained outages, exhausted queues, disk risk or backup failures. Show per-sensor stale/offline status to authorized tenants. Keep platform metrics, alerts and configuration restricted to platform operators.
- **OBS-03.** Write runtime logs as structured container output where supported. Retrieve them with `docker compose logs` and enforce per-service rotation. Keep command audit events in tenant-scoped PostgreSQL records. Save firing and resolved alarm notifications to a separate local persistent ledger that remains writable during a TimescaleDB outage. Export alarm history and diagnostic logs to the designated soak directory. Redact telemetry values, secrets and credentials.
- **OBS-04.** Alerting and history must work during internet loss. Expose missing metrics or a stale alarm receiver as unknown/degraded. Record monitoring gaps during laptop sleep or shutdown on restart. During the pilot, inject faults and verify trigger timing, local visibility, resolution, deduplication and persistence across restarts.

### Fault test requirements

- **FT-01.** Add a repeatable Compose fault profile with deterministic simulator seeds, two tenants with overlapping IDs, disposable volumes and a manifest of injected faults. Run the short suite against the full MQTT-to-TimescaleDB path in CI. Run extended network, capacity and restore tests during the pilot in an isolated stack.
- **FT-02.** For every case, collect pre-fault and post-drain event counts by tenant, fault and recovery timestamps, alert transitions, queue depth and age, relevant logs, and tenant-scoped query results. Check all generated IDs reach one terminal outcome. Require zero duplicate rows, zero unexplained losses and no cross-tenant reads or commands. Explicitly induced drops must match the producer loss count.
- **FT-03.** Cover simulator silence, broker restart, lost gateway receipt, invalid or conflicting events, single-tenant overload, gateway and backend outages, stale trends, lost command ACKs, overdue backups and point-in-time restore. Validate warnings and critical alarms against the applicable thresholds and confirm resolution and persisted history. The scenarios and suite assignments are defined in [architecture.md](architecture.md).

## 5. Multi-tenancy

- **TEN-01.** Require an authenticated tenant context on every data-plane and operator request. Operators can access only their assigned tenants. Resolve active tenant from an authorized membership, and gateway and simulator tenant scope from service credentials. Each tenant has its own sensor registry, events, commands, audit trail and trends. Include `tenant_id` in resource keys, relationships, queue records, cache keys, deduplication and aggregate grouping. The same sensor and event IDs may exist independently across tenants.
- **TEN-02.** Use a shared TimescaleDB instance with tenant-scoped queries and writes. Enforce scope at the service and relational access layers and use database row-level security on supported tables. Keep continuous aggregates and materialization relations private to the backend. Expose only queries that bind the authenticated tenant before any aggregation or rollup. Isolate tenant queue budgets, apply per-tenant ingestion and query limits, and keep dashboard results and command dispatch scoped to the selected tenant.
- **TEN-03.** Seed two tenants with overlapping IDs and distinct values. Verify unauthorized cross-tenant reads, writes, trends, commands, acknowledgments and replays are denied without exposing resource details. Verify valid traffic for one tenant does not change another tenant’s counts or sensor state. Repeat isolation checks after backup and restore.

## 6. Acceptance and implementation order

| ID | Acceptance for the initial laptop run |
|---|---|
| AC-01 | Compose starts from a clean clone. Browser displays seeded telemetry across all four resolutions. Restart restores data and sensor state. |
| AC-02 | Soak stays within ±5% of 1 GB/day over active runtime. Reconcile all generated and committed events after drain, with zero unexplained losses and zero duplicate rows. Backlog drains within 5 minutes after the two-minute fault test. |
| AC-03 | During steady state, p95 gateway receipt to commit ≤3 s and p95 trend API latency ≤500 ms with five concurrent readers across representative time ranges and all resolutions. Document the exact test mix and measure again at day 15. |
| AC-04 | Validate bucket edges, weekly boundaries, weighted means, late arrivals and gaps against deterministic fixtures. Fresh committed data becomes visible in the current trend within 30 s under steady load. |
| AC-05 | Online sensor commands reach confirmed state within 5 s at p95. Pause stops new samples, resume restarts them and an offline command cannot report success without ACK. Test duplicate requests, stale versions, restart and expired commands. |
| AC-06 | The run report explains resource growth, interruptions, retention and capacity bottlenecks with measured data. CI checks the short test workloads. The 15-day run executes locally. |
| AC-07 | Exercise a real multi-day disconnect in the fault profile, or model seven days of backlog using accelerated generation and separately verify a continuous overnight network fault. Verify WAN-only isolation, stale/offline transitions, queue limits, catch-up, chart repair and per-tenant reconciliation. Record which test was run. |
| AC-08 | Restore from the independent backup into fresh volumes, measure RPO and restore time, reconcile commands and verify tenant isolation. |
| AC-09 | For all six sensor types, submit valid and invalid events, including a mixed batch. Concurrently replay a valid event and reuse its ID with modified content. Verify one committed row, duplicate success for unchanged payloads and explicit conflict for changed payloads. |
| AC-10 | Restart the MQTT broker and simulate a lost application receipt after spool commit. Verify that the producer keeps its outbox until gateway receipt, replays unchanged bytes, and yields one committed event. Verify tenant topic ACLs and binary message validation. |
| AC-11 | Induce a gateway/backend partition, a full-queue condition and an overdue backup. Verify warning/critical transitions, alert recovery, durable local history during database downtime and tenant access boundaries. |
| AC-12 | Run the short fault suite in CI and the extended suite in the pilot. Attach per-scenario evidence covering detection, alerting, recovery and per-tenant event reconciliation. |

Implementation sequence: M0 repository, rules and Compose skeleton; M1 tenant identity and isolation, simulator, durable gateway and Java/Timescale ingest; M2 aggregated API and React trends; M3 acknowledged sensor controls and fault tests; M4 calibration, pilot, soak and report. Split milestones into single-task PRs and track them in `plan.md`. Suggested source paths: `simulator/`, `gateway/`, `backend/`, `frontend/`, `perf/` and `scripts/`.

## 7. GitHub branching and CI

Reference: [Invoice Intel CI policy at the reviewed commit](https://github.com/utkarshmankad/invoice-intel/blob/c62b77ab8dccabffa43323ac5ef5dc7573e9a50f/docs/ci.md).

- **GIT-01.** Use protected, releasable `main` and short-lived branches named `<type>/<task-id>-<description>` with one task per PR. Rebase behind branches and tag releases on `main`. Use configuration flags for incomplete multi-PR features. Require Conventional Commit PR titles and list requirement IDs in the body.
- **GIT-02.** Apply the Invoice Intel `main-trunk` ruleset to the default branch after the first bootstrap commit and a verified CI run. Require PRs, squash-only merges, linear history, resolved review threads, zero required approvals and the strict GitHub Actions check `CI gate`. Block force-push and deletion of `main`. Use zero bypass actors and auto-delete merged branches. Enable Dependabot, secret scanning and push protection where available. Verify ruleset and security-feature availability for the chosen GitHub visibility and plan before marking M0 complete.
- **CI-01.** Trigger CI on PRs to `main`, pushes to `main` and manual dispatch. Cancel superseded PR runs. Use least-privilege permissions and SHA-pinned actions. Run PR hygiene, tracked secrets/data guards and gitleaks, actionlint, Spotless, Java unit/ArchUnit and Testcontainers integration tests, merged JaCoCo line coverage ≥85%, SpotBugs/FindSecBugs, CodeQL, high/critical dependency and GPL/AGPL review, hadolint, Trivy fixable high/critical image scan, Compose smoke test and Gatling performance assertions. Add frontend type-check, ESLint, unit tests and production build. Adapt the Invoice Intel data guard to forbid captured telemetry, secrets, database files and benchmark outputs.
- **CI-02.** `CI gate` summarizes all jobs, runs even if dependencies fail, and rejects failed or cancelled jobs. Permit intentional prerequisite skips before build components exist. Once a component lands, its expected checks must fail if build inputs disappear. Docs-only PRs skip performance only. Run the Compose smoke test with synthetic sensors and disposable credentials. Verify startup, authorized ingest and trend read, duplicate replay, and a sensor off/on round trip as those capabilities land. Publish CI reports for 14 days.
- **CI-03.** Nightly at 03:00 IST, run PIT on critical ingestion and control code and rescan fresh images with Trivy. Nightly jobs are outside the merge gate. Add CODEOWNERS, a PR template and weekly grouped Dependabot updates for Gradle, npm, Docker and Actions.
